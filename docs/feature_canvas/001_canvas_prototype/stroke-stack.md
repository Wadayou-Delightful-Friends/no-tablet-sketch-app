# ストロークスタック — 描いた記録の持ち方

## 決めたこと

- 描かれたストロークは `domain/stroke/stroke_stack.ts` の **StrokeStack**
  （= `Stroke[]`、末尾が最新）に描いた順で積む
- `Stroke` は `stroke_id` / `radius`（ワールド単位）/ `points: WorldPoint[]`
- 点の追記は `appendPoint` に一本化。**stroke_id が末尾ストロークと同じなら続きに
  追記、変わっていたら新規ストロークを積む**

## なぜ「順序付きスタック」か

- メリット:
  - 描画がそのまま「下から順に重ねて描く」ループになる（重なり順 = 配列順）
  - 将来の undo が「末尾から取り消す」操作として自然に実装できる
    （ユーザー要望の「ストロークごとの記録をスタックして残す」に対応）
  - ストローク単位で保持するので、選択・削除・移動などの編集機能に発展できる
- デメリット:
  - 1 枚のビットマップに焼き込む方式に比べ、ストローク数に比例して
    描画コストとメモリが増える（現段階の規模では問題にならない）

## なぜ末尾比較だけでストロークを区切るか

write コマンドが 1 点ずつ届く前提で、「新しいストロークが始まった」ことを
専用コマンドなしに判定する必要がある。全スタックから stroke_id を検索する案と
比べて：

- メリット: O(1) で判定できる。完了済みの古いストロークへ誤って追記されない
- デメリット: 複数コントローラの write が同時に交互に届くと、同じ stroke_id でも
  別ストロークに分割される

**判断根拠**: 現段階は単一コントローラなので交互到着は起きない。複数コントローラを
繋ぐ段階では「コントローラごとにスタックを分けて描画時に合成する」方針で
対応する想定（stroke_id に controller_id が含まれているのはこのため）。

## スタックをミューテーション（破壊的更新）にした理由

カメラ（不変・毎回新オブジェクト）と対照的に、スタックは `push` で追記する。

- メリット: 描画中は毎フレーム点が増えるため、都度スタック全体をコピーすると
  ストローク長に比例した無駄が出る。追記だけなら O(1)
- デメリット: 参照共有によるバグ（外から配列をいじれる）の余地が残る

「小さく置き換わるもの（カメラ）＝不変、積み上がるもの（ストローク）＝可変」
という基準で使い分けている。
