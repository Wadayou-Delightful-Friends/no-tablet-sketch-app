# コマンドモデル — 操作を Command として表現する

## 決めたこと

すべての操作は `domain/command/command.ts` の **Command**（直列化可能なプレーンな
オブジェクト）として表現し、`createCommandDispatcher` が Scene に適用する。
今回実装したのは 3 種類：

| type | 内容 | ペイロード |
| --- | --- | --- |
| `write` | 書く（1 コマンド = 1 点） | `stroke_id`, `radius`, `point`（画面座標） |
| `move` | カメラ移動 | `delta`（画面上の移動量 px） |
| `zoom` | 拡大縮小 | `anchor`（画面上の固定点）, `factor`（scale に掛ける倍率） |

全コマンドに共通の envelope（`controller_id` / `seq` / `timestamp`）は
既存の `WriteCommand` の形式に合わせた。

## なぜコマンドベースか

- メリット:
  - 入力デバイス（マウス・タッチ・将来のリモートコントローラ）と、
    キャンバスのロジックが Command という 1 枚のインタフェースで切れる
  - Command は直列化できるので、そのままネットワーク越しに送れる
    （このアプリの Controller/Display 分離構成に将来つながる）
  - 操作の記録・再生（リプレイ）が自然にできる
- デメリット:
  - 直接メソッドを呼ぶより一段まわりくどい（型定義と分岐が増える）

## Move/Zoom を「差分ベース」にした理由

`command.ts` の元のコメント案は「絶対値を送って last-write-wins（LWW）で
順序の乱れに耐える」だった。今回は**差分ベース**（move=移動量、zoom=倍率）に変更した。

差分ベース（採用）:

- メリット:
  - 入力層が現在のカメラ状態を知らなくてよい（DOM イベントの生の差分を
    そのままコマンド化できる。入力層に状態が要らない）
  - zoom の anchor 固定計算を domain に集約でき、入力層が単純になる
- デメリット:
  - コマンドが 1 つ欠落・重複すると結果がずれたまま残る（LWW 耐性がない）
  - 複数コントローラが同時にカメラを動かすと合成結果が予測しにくい

絶対値ベース（不採用）:

- メリット: 欠落・順序乱れに強い（最後の 1 つだけ適用すれば正しい状態になる）
- デメリット: 入力層が「現在のカメラ」を参照して絶対値を計算する必要があり、
  入力層と Scene の間に依存が増える

**判断根拠**: 現段階はローカル単一ソース（デモの 1 入力のみ）で、
欠落も順序乱れも起きないため、LWW 耐性は必要ない。将来ネットワーク越しに
複数コントローラを繋ぐ段階になったら、カメラ系コマンドだけ絶対値へ
戻すことを再検討する（write は元から点ベースで欠落に強い設計なので影響なし）。

## write が「1 コマンド = 1 点」である理由（既存設計の踏襲）

線分ではなく点で送ることで、1 点欠落しても隣どうしを繋げば線が途切れない。
ストロークの区切りは開始/終了コマンドではなく `stroke_id` の変化で表現するため、
「開始コマンドだけ欠落して線が繋がらない」事故も起きない。

## radius の座標系

`WriteCommand.radius` は**画面 px**（ユーザーが選んだペンの太さ）。
ディスパッチャが書き込み時点の scale で割って**ワールド単位**に変換して保存する。
これにより「描いた瞬間は指定した太さに見え、その後はズームに追従して拡縮される」
という直感的な挙動になる。
