# 座標系とカメラ — 無限キャンバスの表現方法

## 決めたこと

- 座標系を 2 つに分ける
  - **ScreenPoint**: 画面ピクセル座標。DOM 入力と描画先が使う
  - **WorldPoint**: 無限キャンバス上の固定座標。ストロークはこちらで保持する
- 両者は **カメラ**（`domain/camera/camera.ts`）で相互変換する

  ```
  screen = world * scale + translation   （translation は画面 px）
  ```

- 「無限」は、**ストロークを world 座標のまま保持し、描画のたびにカメラで
  screen へ変換する**ことで表現する。キャンバス自体に大きさの概念を持たせない

## なぜ座標を 2 つの型に分けるか

`x, y` の構造は同じでも、画面座標とワールド座標を取り違えると
「ズームすると絵がずれる」類のバグになり、実行するまで気づけない。
別の型にしておけば、取り違えはコンパイルエラーとして現れる。
（`point.ts` に元からあったコメントの方針に従った）

- メリット: 座標系の混同がコンパイル時に検出できる。関数シグネチャだけで
  どちらの座標系を受け取るかがわかる
- デメリット: 構造が同一の型が 2 つ存在し、変換関数を通す一手間が増える

## なぜ「カメラ方式」か（代替案との比較）

代替案は「描画済みピクセルを巨大なビットマップ（タイル）として持ち、
表示域だけ切り出す」方式だった。

カメラ + ベクタ保持（採用）:

- メリット:
  - 本当に無限（world 座標は number の範囲まで広がる。タイルの確保が不要）
  - ズームしても線が荒れない（描画時に毎回ベクタから描くため）
  - 保持するのは点列だけなのでメモリが軽い
- デメリット:
  - ストローク数が増えるほど毎フレームの再描画コストが増える
    （対策は rendering.md を参照）

タイル方式（不採用）:

- メリット: ストローク数に依存しない描画コスト
- デメリット: 拡大でピクセルが荒れる、タイル管理が複雑、メモリを食う

現段階は「正しく動く最小構成」を優先し、カメラ方式を選んだ。

## zoomAt の仕組み

ズームは「カーソル直下の world 点が、ズーム後も同じ画面位置に残る」ように
translation を再計算する。これがないと拡大のたびに画面中心へ吸い込まれる
不自然な動きになる。

```
worldAtAnchor = screenToWorld(camera, anchor)
newScale      = scale * factor
newTranslation = anchor - worldAtAnchor * newScale
```

検証は `test/camera.test.ts` の「zoomAt は anchor 直下の world 点を動かさない」。

## カメラ関数を純粋関数（新しい Camera を返す）にした理由

- メリット: テストが入出力の比較だけで書ける。変更途中の状態が描画側へ漏れない
- デメリット: 毎回オブジェクトを生成するコスト（カメラは小さいので無視できる）

一方、ストロークのスタックは追記が主体なのでミューテーション方式にした
（理由は stroke-stack.md）。使い分けは「小さく置き換わるもの＝不変、
積み上がるもの＝可変」という基準による。
