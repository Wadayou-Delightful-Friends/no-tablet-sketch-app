# 座標設計ドキュメント — 無限キャンバス描画ツール

> このドキュメントは、このプロジェクトの背景をまったく知らない人が読んでも、
> 「なぜこの設計になっているのか」を理解できることを目的にしています。
> 専門用語には初出時に説明を添えています。

---

## 0. 前提知識(このアプリの何が普通と違うのか)

一般的なお絵かきアプリは、**指で触る画面と、絵が表示される画面が同じ**です。
タブレットに指で線を引けば、その場所に線が出ます。

このアプリは違います。**入力する端末と、表示する端末が物理的に別**です。

- **スマートフォン = コントローラ**。指の位置を送るだけ。**絵は表示しない。カメラ（表示範囲）も持たない。**「馬鹿なコントローラ」と呼んでいます。
- **PC = ディスプレイ**。絵を表示し、拡大・移動（カメラ操作）を行い、**すべての座標計算を担う**。

さらに、使い方に2パターンあります。

| パターン | 構成 | カメラ操作 |
|---|---|---|
| **1対1** | 各自がディスプレイとコントローラを1台ずつ持ち、オンラインで繋ぐ | 各自が自分のカメラを自由に動かす |
| **1対多** | 1台のディスプレイを、複数のコントローラで共有する | **オーナーだけ**がカメラを動かせる |

この「入力と表示の分離」が、座標の設計を普通のアプリより一段複雑にしています。
このドキュメントは、その複雑さをどう整理したかを説明するものです。

なお、キャンバスは **「無限」** です。ユーザーはどこまでも上下左右に移動でき、拡大・縮小もできます。
（ただし後述するとおり、「無限」は数学的な無限ではなく、実用上の無限です。）

## 1. なぜ座標が難しいのか — 4つの「座標空間」

このアプリでは、同じ「点」でも、**どの基準で測った座標か**によって意味が変わります。
基準の違うものを「座標空間」と呼びます。全部で4つあります。

| 座標空間 | 例 | 何を基準にした座標か | どこで登場するか |
|---|---|---|---|
| **正規化座標** | `(0.5, 0.5)` | コントローラの入力面を `0.0〜1.0` で表したもの。中央なら `(0.5, 0.5)` | スマホ → PC の通信 |
| **スクリーン座標** | `(960, 540)` | PC画面上のピクセル位置 | PC画面への表示 |
| **ワールド座標** | `(1234.5, -800.2)` | 無限キャンバス上の論理的な位置。カメラを動かしても変わらない | 絵のデータの保存 |
| **チャンク座標** | `(2, -2)` | 無限キャンバスを格子状に区切ったときのマス目の位置 | （今は未使用・将来用） |

**問題は、これら4つがすべて `{ x: 数値, y: 数値 }` という同じ形をしていること**です。
プログラム上で見分けがつかないため、うっかり取り違えると、

- スクリーン座標を、ワールド座標のつもりで扱ってしまう
- 変換をかけ忘れる／二重にかけてしまう

といったバグが起きます。しかも取り違えのパターンは12通りあり、実行するまで気づけません。
**この「空間の取り違え」を防ぐことが、設計の主目的のひとつ**です。

### データの流れ

```
[コントローラ]                         [ディスプレイ = PC]
 カメラなし・描画なし                    カメラあり・座標計算を担う

   正規化座標 (0〜1)
   ─────────────────►  スクリーン座標  ───►  ワールド座標  ───►  保存
                        (画面ピクセル)        (キャンバス上)
```

座標の変換は、**必ずディスプレイ側の1か所を通る**ように設計しています（後述）。

## 2. 設計判断の一覧

各判断について「決定」と「理由」を示します。

### 判断0: 描画技術は Canvas2D を使う

**決定**: ブラウザ標準の Canvas2D を使う。（WebGL は使わない）

**理由**:
プロ向けイラストツールではなく、凝ったブラシ表現は不要。Canvas2D なら、

- カメラの拡大・移動を **ブラウザに任せられる**（自前で全点を計算し直す必要がない）
- 線の太さや角の処理をブラウザがやってくれる
- 「遠くまで移動すると座標の精度が落ちる」という WebGL 特有の問題が**そもそも起きない**

WebGL は表現力と処理能力で勝りますが、線の形状を自前で作る必要があり、コストが見合いません。

---

### 判断1: 座標変換は `Viewport` という1か所に集約する

**決定**: 座標を変換する計算式を、アプリのあちこちに書かない。
`Viewport`（ビューポート）という専用の部品を1つ作り、**変換はすべてそこに通す**。

**理由**:
`(x - パン量) × 拡大率` のような変換式がコード中の10か所に散らばると、
符号ミスや計算順序ミスが必ず起き、修正も困難になります。
1か所に集約すれば、間違いはそこだけを見れば済み、内部の作りを変えても他に影響しません。

`Viewport` は「変換の唯一の窓口」として、こういう役割を持ちます。

- 正規化座標 → スクリーン座標
- スクリーン座標 → ワールド座標
- 長さの変換（後述のヒット判定用）
- 今画面に映っているワールド範囲の計算（表示の高速化用）
- 拡大時に、指の位置を中心に据えたまま拡大する処理

---

### 判断2: 座標空間を「型」で区別する（ブランド型）

**決定**: 4つの座標空間を、プログラムの「型」レベルで別物として扱う。
`WorldPoint`（ワールド座標）・`ScreenPoint`（スクリーン座標）・`NormalizedPoint`（正規化座標）を別の型にする。

**理由**:
前述のとおり、4空間はすべて `{x, y}` という同じ形なので、素のままでは取り違えを検出できません。
型を分けておくと、

```
スクリーン座標を、ワールド座標を要求する関数に渡した
  → プログラムを実行する前に、エラーとして止まる
```

つまり**バグを、動かす前の段階で潰せる**。後からこの仕組みを足すのはほぼ不可能なので、最初から入れます。

長さについても同様に、`WorldLength`（ワールド上の長さ）と `ScreenLength`（画面上の長さ）を分けます。
これは「指で押した位置の10ピクセル以内にある線を選ぶ」といった判定で効きます。
その「10ピクセル」は**画面上の10ピクセル**であって、ワールド上の長さに換算すると拡大率で変わるためです。
（この区別を怠ると「縮小表示すると何も選択できない」バグになります。）

---

### 判断3: 絵のデータは「配列を分けて」持つ（SoA）

**決定**: 1本の線を構成する点の列を、
`{x, y}` オブジェクトの配列ではなく、**x だけの配列・y だけの配列に分けて**持つ。
しかも、数値専用の効率的な配列（`Float64Array`）を使う。

**理由**:
無限キャンバスには、大量の線が溜まりえます。仮に10万本・1本あたり平均200点なら、合計2000万点。

`{x, y}` というオブジェクトは、見た目より重く（1個で40〜56バイト）、
2000万個も作ると**合計約1GB**を消費し、さらにメモリ管理（GC）の処理でアプリが定期的にカクつきます。

x・y を別々の効率的な配列にすると、同じ2000万点が**約320MB**で済み、カクつきの原因も消えます。

**ただし、この「配列を分ける」方式は書きにくい**ので、影響範囲を `WorldStroke`（1本の線を表す部品）の内部だけに閉じ込めます。
外から見た使い方は普通のまま保ちます。こうすれば、後で方式を変えるのも容易です（後述の不変条件を守る限り）。

---

### 判断4: 座標軸の向きと原点

**決定**:
- Y軸は**下向き**（画面と同じ。下に行くほど数値が増える）
- 新規キャンバスの**初期表示の中央を原点 `(0, 0)`** とする
- **負の座標を許容する**（左や上に移動すれば座標はマイナスになる。それが正常）

**理由**:
Y軸を画面と揃えると、変換に上下反転が入らず、バグが減ります。
無限キャンバスでは負の座標は当たり前なので、それを避けようと原点をずらす設計は、いずれ破綻します。

---

### 判断5: 拡大・縮小の範囲を制限する（クランプ）

**決定**: 拡大率に上限・下限を設ける。範囲は **1/8倍〜8倍**、間を**20段階**に区切る。
段階は等比（1段階ごとに一定の倍率を掛ける方式）で刻む。1段階あたり約1.26倍。

**理由**:
無制限に拡大・縮小できると、ユーザーが自分の位置を見失います。
段階を「足し算」ではなく「掛け算」で刻むのは、そうしないと縮小が異常に速く・拡大が異常に遅く感じられるためです。
（Canvas2D を選んだので、この制限は精度保護のためではなく、純粋に使い勝手のためです。範囲は後から自由に調整できます。）

拡大の中心は**指の位置（またはピンチの中心）**に合わせます。画面中央基準にすると、拡大のたびに目的の場所が画面外へ逃げてしまうためです。

---

### 判断6: 描いている最中の線と、確定した線を分ける（wet / dry 分離）

**決定**: 「今まさに描いている途中の線（wet）」と「描き終わって確定した線（dry）」を別扱いにする。
確定済みの線は、画面に映っている分だけを描き直す（表示範囲外は描かない = カリング）。

**理由**:
確定済みの何万本もの線を毎フレーム描き直すのは非現実的です。
描画中の1本だけを軽く再描画し、確定済みは効率的に扱うことで、遅延を抑えます。

各線に「その線を囲む長方形（バウンディングボックス）」を持たせておきます。
これにより「画面に映っているか」を高速に判定でき、将来さらに高度な高速化にも発展させられます。

---

### 判断7: 描画中はカメラをロックする（1対多のみ）

**決定**: 1対多で、誰かが線を描いている最中は、オーナーのカメラ操作（移動・拡大）を止める。
ただし**タイムアウト付き**にする。

**理由**:
コントローラは正規化座標（画面上の割合）しか送りません。
描いている途中でカメラが動くと、「同じ指の位置」が別のワールド座標に化けてしまい、線が歪んだり指からずれたりします。
そこで、描画中はカメラを固定します。

タイムアウトを付けるのは、通信の都合で「指を離した」という信号が届かないと、
カメラが永久に動かせなくなる（デッドロック）のを防ぐためです。一定時間入力がなければ、その線を強制的に確定してロックを解きます。

（この問題は1対多だけのものです。1対1では、自分のカメラは自分しか動かさないので起きません。）

---

### 後回しにした判断

以下は「今は決めず、必要になってから対応する」としたものです。いずれも、後から足せるよう設計に余地を残してあります。

| 項目 | 理由 |
|---|---|
| 空間インデックス（線を高速検索する仕組み） | 各線がバウンディングボックスを持つので、後から被せられる |
| 通信データの圧縮 | 通信部分は独立しているので、実測して遅ければ後で対応 |
| チャンク（キャンバスを格子で区切る仕組み） | 現状の設計では不要。必要になれば導入できる |

## 3. アーキテクチャの全体像

各部品の役割と、データの流れです。

```
[コントローラ]                        [ディスプレイ = PC]
 ・カメラを持たない                     ・カメラを持つ(この端末だけの状態)
 ・絵を描画しない                       ・座標変換の唯一の担い手
      │
      │ 送るのは正規化座標 {x,y}∈[0,1] のみ
      │ （＋ どのコントローラか, 筆圧, 時刻）
      ▼
 ┌──────────────────────────────────────────┐
 │ Viewport（座標変換の唯一の窓口）           │
 │   正規化座標 → スクリーン座標              │
 │   スクリーン座標 → ワールド座標            │
 │   画面上の長さ → ワールド上の長さ          │
 │   拡大・移動の計算                         │
 └──────────────────────────────────────────┘
      │
      │ ワールド座標（型で守られた入口）
      ▼
 ┌──────────────────────────────────────────┐
 │ WorldStroke（1本の線）                     │
 │   ・内部は x配列 / y配列 に分けて保持       │
 │   ・入口は push() ひとつだけ               │
 │   ・出口は forEachPoint() ひとつだけ        │
 │   ・自分を囲む長方形(BBox)を持つ            │
 └──────────────────────────────────────────┘
      │
      │ ワールド座標のまま渡す
      ▼
 ┌──────────────────────────────────────────┐
 │ CanvasRenderer（実際の描画。Canvas依存）    │
 │   カメラ変換をブラウザに委譲して描く        │
 │   画面外の線は描かない(カリング)            │
 └──────────────────────────────────────────┘
```

要点は3つです。

1. **座標変換は `Viewport` にしか存在しない。**
2. **空間の取り違えは、プログラムを動かす前に型が止める。**
3. **大量の点は、変換されずそのまま Canvas に渡され、ブラウザが表示する。**

## 4. 守らなければならないルール（不変条件）

この設計の利点は、以下が守られている限りで成立します。
**破ると、「後から変えられる」はずだった部分が「変えられない」ものに変わります。**

1. **`WorldStroke` の内部配列を、外部に直接見せない。**
   出入り口は `push()`（点の追加）・`forEachPoint()`（点の読み取り）・`boundingBox`（囲み枠）だけに限る。
   → これを守る限り、内部の持ち方（配列の分け方や数値の精度）を後から自由に変えられる。**この設計で最も重要で、最も壊れやすい一線。**

2. **座標変換の式を `Viewport` の外に書かない。**
   他のファイルで `(x - パン量) × 拡大率` のような式を見つけたら、それはバグの前触れ。

3. **座標の型を「無理やり別の型に見せかける」書き方（型キャスト）をしない。**
   決められた生成関数の内部だけを例外とする。（自動チェックで縛ることを推奨。）

4. **描き終わった線は「確定処理」を必ず呼ぶ。**
   忘れると、確定済みの線が余分なメモリを抱え続ける。

5. **絵のデータを扱う中心部（domain）に、ブラウザ固有のもの（Canvas や画面イベント）を持ち込まない。**
   ブラウザ依存は表示担当（CanvasRenderer）に閉じ込める。

## 5. 実装で最初に出会う注意点

議論の中で確認した、実装初日に踏みやすい落とし穴です。

- **画面の精細度（devicePixelRatio）の扱い**
  高精細ディスプレイ対応の倍率計算は、表示担当（CanvasRenderer）側だけで行う。
  `Viewport` はこの倍率を知らないままにする。混ぜると、にじみ対応のバグが中心部まで染み出す。

- **線の太さが拡大率で変わること**
  絵の線は「拡大すると太くなる」のが正しい（紙の線を虫眼鏡で見るのと同じ）。
  一方、選択枠・グリッド線・カーソルなどは「拡大しても一定の太さ」であってほしい。
  これらは太さの扱いが逆なので、別々に処理する必要がある。

- **コントローラとディスプレイの縦横比を合わせること**
  スマホの入力エリアと、PCの表示エリアの縦横比が違うと、
  スマホで描いた正方形が、PCでは長方形に潰れてしまう。
  接続時にディスプレイ側から縦横比を伝え、コントローラはその比率で入力エリアを作る。
  PC側の画面サイズが変わったら、伝え直すのを忘れないこと。
  （縦横比はカメラの情報ではなく接続時に決まる固定値なので、「コントローラはカメラを持たない」という原則には反しない。）

## 用語集

| 用語 | 意味 |
|---|---|
| **カメラ / ビューポート** | 無限キャンバスの「どこを・どれくらいの拡大率で映すか」という状態。移動量と拡大率で表す。 |
| **ワールド座標** | キャンバス上の論理的な位置。カメラを動かしても変わらない、絵の「本当の」座標。 |
| **スクリーン座標** | PC画面上のピクセル位置。カメラを動かすと同じ絵でも変わる。 |
| **正規化座標** | 入力面を `0.0〜1.0` の割合で表した座標。コントローラが送る唯一の座標。 |
| **ブランド型** | 見た目が同じデータを、プログラム上で別物として区別する型の仕組み。取り違えを実行前に検出するために使う。 |
| **SoA（配列を分けて持つ方式）** | 点を `{x,y}` の集まりではなく、x の配列・y の配列に分けて持つ方式。大量データで効率が良い。 |
| **バウンディングボックス（BBox）** | ある線をちょうど囲む長方形。「画面に映っているか」を高速判定するために使う。 |
| **カリング** | 画面に映っていないものを描画対象から除外して、表示を速くすること。 |
| **wet / dry** | 描いている途中の線（wet）と、描き終わって確定した線（dry）の区別。 |
| **クランプ** | 値に上限・下限を設けて、その範囲に収めること。ここでは拡大率に対して行う。 |
| **デッドロック** | 互いに待ち合ったまま先に進めなくなる状態。ここでは「描画中ロックが永久に解けない」状況を指す。 |
