# 座標の正規化 — 通信で届く 0〜1 の座標を画面座標へ戻す場所を決める

## 背景

コントローラ（スマホ）が送る座標は、送信側・受信側どちらの画面サイズにも依存しない
よう **0〜1 の正規化座標**に決まった。しかし `Command` の座標型は `ScreenPoint`
（画面 px）のままで、`useControllerInput.ts` には
「Command 側の座標型名は今後見直す予定」というコメントが残っていた。

その結果 `Command` 型が経路によって 2 つの意味を持っていた。

- ローカル入力 `sketch_input.ts` → 画面 px
- 受信 `useControllerInput.ts` → 正規化座標

辻褄合わせとして `useSketchCanvas.ts` の `handleRemoteMessage` の中で
write / erase だけを `clientWidth` / `clientHeight` 倍していた。ここは
「受信メッセージを描画へ流す入力口」であって座標変換の置き場ではなく、
move / zoom が届き始めたら同じ場所に分岐が増え続ける。

この作業の目的は **正規化 → 画面 px の変換を 1 箇所に集約すること**。

## 決めたこと

### 1. 変換は受信アダプタ層で行う（dispatcher は無変更）

`features/sketch/normalized_command.ts` に `toScreenCommand(viewport, command)`
を新設し、受信経路だけがここを通る。domain（Scene / Camera / dispatcher）は
今まで通り画面 px しか扱わない。

対案は「`createCommandDispatcher` に `getViewport: () => Viewport` を注入し、
dispatcher 内部で変換する」だった。こちらは正規化を唯一の入力形式にできる代わりに、
ローカル入力 `sketch_input.ts` も正規化を送るよう合わせる必要があり、
domain が「描画領域のサイズ」という表示側の都合を知ることになる。

**判断基準は「座標系の変換をどの層の責務とみなすか」**。カメラ変換
（画面 ↔ ワールド）は描画の本質なので domain にあるべきだが、
正規化 ↔ 画面 px は通信フォーマットの都合であり、境界で吸収するほうが層として素直。
domain を触らずに済む点も選択理由になった。

### 2. radius は正規化せず画面 px のまま送る

座標だけ 0〜1 にし、`radius`（ペン・消しゴムの太さ）は px のままにした。

太さは「見た目の物理的な太さ」であって画面サイズに対する比ではない、という理由。
正規化すると大きいディスプレイほど線が太くなるが、それは意図した挙動ではない。
`factor`（ズーム倍率）も座標ではないので同じ扱いで素通しする。

### 3. 正規化座標を表す型は `NormalizedPoint` として point.ts に置く

`schema_common/point.ts` の「構造が同じでも座標系が違えば型を分ける」という
既存方針に従い、`ScreenPoint` / `WorldPoint` に続く 3 つ目として追加した。

ただし **TypeScript はこの区別を強制できない**。どちらも `{ x: number; y: number }`
なので構造的に相互代入できてしまう（実際に確認済み）。したがってこの型は
「読み手への表示」であって安全装置ではない。実際の防御は

- バリデータの 0〜1 範囲チェック（実行時）
- 変換を `toScreenCommand` の 1 箇所に閉じたこと（設計）

が担っている。この事実は `normalized_command.ts` のヘッダーに明記した。

### 4. `sketch_input.ts` は変更しない

PC のマウス入力を Command に変換するローカル入力は、画面 px のまま
dispatcher に直接渡す経路を維持した。ファイル冒頭に「通信層が入ったら削除」と
書かれた暫定の足場であり、今の形のまま動く。スマホなしで描画のデグレを検知できる
手段として残す価値があるため、削除もしていない。

### 5. コマンドの座標範囲チェックを実装した

001 で「値域が未定」として TODO 枠に残していた項目のうち、今回で仕様が確定した
座標の範囲だけを実装した（`validateScreenPoint` → `validateNormalizedPoint`）。

- 位置（`point` / `anchor`）は 0〜1
- 差分（`delta`）は向きを持つので -1〜1

`radius` / `factor` / `seq` / `timestamp` は値域が未定のままなので TODO 枠に残した。

## 方針変更の経緯 — 型引数 `P` を入れて、やめた

当初は `Command<P = ScreenPoint>` と型引数化し、`Command<NormalizedPoint>` で
通信用の形を表す設計を実装した。既定値のおかげで既存の import は 1 箇所も
書き換えずに済み、正規化版を別ファイルへ複製する案（約 40 行の重複）も避けられる、
という判断だった。

これを 2 段階で撤回した。

1. **`Normalized*` エイリアス 5 つを削除** — 使う側で `Command<NormalizedPoint>` と
   直に書くほうが、別名を覚えるより読んで分かる。
2. **型引数そのものを削除** — 決め手は「`P` が取り違えを一切防いでいない」こと。
   `Command` と `Command<NormalizedPoint>` は構造が同じなので相互に代入でき、
   変換を忘れたコードは型検査を通ってしまう。防御になっていない抽象のために
   中核の型定義に 1 段の抽象が乗り、読み手に「`P` に何が入りうるのか」という
   余計な推測を強いるのは割に合わない。

結果として `command.ts` は**完全に無変更**になった。正規化と画面 px の区別は
`toScreenCommand` という関数名と、それが受信経路にしか存在しないことが担う。
型で示していた時と実質的な強度は変わらない。

## 未決事項 / 今後

- **アスペクト比の歪み**: スマホの描画領域と PC の canvas の縦横比が違うと、
  正規化座標は領域全体を引き伸ばして写すため円が楕円になる。幅基準に統一して
  レターボックスする等の対処が要るが、座標系の整理とは別の判断なので分けた。
- **move / zoom はコントローラ側が未送信**。型と変換とバリデータは用意したが、
  実際に送るのはピンチ・ドラッグの入力を実装してから。
- `radius` / `factor` / `seq` / `timestamp` の値域は未定のまま。
- `sketch_input.ts` の削除時期。
