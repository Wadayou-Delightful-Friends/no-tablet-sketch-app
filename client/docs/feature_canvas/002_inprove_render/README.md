# 002 座標設計の見直し — 新設計との比較と採否

[Architect/coordinate-design.md](../Architect/coordinate-design.md)（新設計）と
001 のプロトタイプ実装を比較し、部分採用した記録。
001 の各ドキュメント（[coordinate-system.md](../001_canvas_prototype/coordinate-system.md) 等）の
判断を前提とし、変更・追加した点だけをここに書く。

## 採否の一覧

| 新設計の提案 | 採否 | 対応 |
|---|---|---|
| 座標変換を 1 か所（Viewport）に集約 | ✅ 採用 | 既存の `camera.ts` をそのまま集約先にする（改名はしない） |
| ズーム倍率のクランプ（判断5） | ✅ 採用 | `ZoomSettings` としてパラメータ化（後述） |
| ワールド原点 = 初期表示の中央（判断4） | ✅ 採用 | `createCamera` / `createScene` が原点の画面位置を受け取る |
| 長さの変換（画面 px ⇔ ワールド） | ✅ 採用 | `screenLengthToWorld` / `worldLengthToScreen` を camera.ts に追加 |
| ストロークの点列を内部に閉じ込める | ✅ 採用 | 入口 `push()`・出口 `forEachPoint()` のみ公開（後述） |
| ブランド型（型レベルの座標系区別） | ❌ 不採用 | コントローラ担当が既存の point 型で開発中のため（後述） |
| カメラ変換のブラウザ委譲（setTransform） | ❌ 不採用 | 旧設計（JS で全点 world→screen 変換）を優先する決定 |
| コントローラは正規化座標のみ送る | 保留 | Command は ScreenPoint のまま。通信層で「水際の変換」（後述） |
| SoA（x/y 別の Float64Array） | 保留 | カプセル化により将来 Stroke 内部だけで差し替え可能 |
| BBox・カリング・wet/dry 分離 | 保留 | 利用箇所（性能問題）が出てから。「先回りしない」（AGENTS.md） |
| 描画中カメラロック（1対多） | 保留 | 通信実装時に検討 |

## ズームクランプ — 範囲・段階数はパラメータで調整する

`camera.ts` に `ZoomSettings { minScale, maxScale, stepCount }` を定義し、
`zoomAt` が引数として受け取って scale をクランプする。
数値はロジックにハードコードせず、既定値は `DEFAULT_ZOOM_SETTINGS`
（1/8〜8倍・20段階）に一元化した。範囲や段階数の調整はこの値の変更だけで済む。

- 「1段階あたりの倍率」は `zoomFactorPerStep(settings)` で等比
  `(maxScale / minScale)^(1 / stepCount)` として導出する。等差ではなく等比なのは、
  等差だと縮小側が異常に速く・拡大側が遅く感じられるため（新設計 判断5）
- 段階を刻む主体は入力層（ホイール 1 目盛り＝1 段階など）。domain は
  factor を掛けて範囲にクランプするだけで、段階の概念を持たない
- Canvas2D 採用により精度保護は不要なので、この制限は純粋に
  「ユーザーが位置を見失わないため」の使い勝手の制限

## ワールド原点 = 初期表示の中央

`createCamera(worldOriginOnScreen)` / `createScene(worldOriginOnScreen)` に
「ワールド原点を置く画面位置」を渡す。表示エリアの中央を渡せば
「新規キャンバスの中央 = world (0,0)」になる（新設計 判断4）。
画面端を原点にすると、左・上へ描くだけで座標が負に偏り、原点の位置に
意味がなくなる。負のワールド座標は無限キャンバスでは正常な値として扱う。

## ストロークの点列カプセル化

`Stroke` の `points: WorldPoint[]` の公開をやめ、closure に隠して
入口 `push()`・出口 `forEachPoint()` だけにした（`radius` / `stroke_id` は
読み取り専用のまま公開）。

- 目的: 内部の持ち方を利用側に固定させないこと。大量の点で性能問題が出たら、
  x/y 別の `Float64Array`（SoA）へ **Stroke の内部だけで** 差し替えられる
- 守ること: 点列の配列を直接返す口を作らない。作った瞬間、内部表現が
  外部インタフェースに固定され、この設計の利点が消える
- BBox（バウンディングボックス）は新設計に含まれるが、利用箇所（カリング）が
  まだないため追加していない。必要になったら forEachPoint の1パスで初期構築できる

## ブランド型の不採用と、001 ドキュメントの訂正

新設計はブランド型（`WorldPoint` 等を型レベルで別物にする仕組み）を
「後から入れるのはほぼ不可能」として推奨していたが、**不採用**とした。
コントローラ担当がすでに既存の point 型を使って開発を進めており、
型の互換性を壊す変更は今行うべきでないため。

あわせて訂正: [001 の coordinate-system.md](../001_canvas_prototype/coordinate-system.md) にある
「別の型にしておけば、取り違えはコンパイルエラーとして現れる」は
**実際には成立していない**。TypeScript は構造的型付けのため、構造が同じ
`ScreenPoint` と `WorldPoint` は相互に代入できてしまう。現状の型分けは
「シグネチャで意図を示すドキュメント」としてのみ機能する。取り違え防止は
命名（`worldPoint` / `screenPoint` を変数名に含める）と
「変換式を camera.ts の外に書かない」規律で運用する。

## コマンドの座標系は ScreenPoint を維持（水際の変換）

新設計では「コントローラは正規化座標（0〜1）のみ送る」が、
コントローラからの実際の受信仕様はまだ確定していない。そこで domain の
`Command` は現状どおり ScreenPoint を持ち続け、将来コントローラから
正規化座標（や別の形式）が届いたら、**通信の受信アダプタが Command 化する前に
画面座標へ変換する**（アダプタパターンによる水際の変換）。
仕様が何であれ影響が通信層に閉じ、domain は変更不要になる。
