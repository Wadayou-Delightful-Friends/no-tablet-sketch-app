# 002 消しゴムの描画設計 —「消す」をどう表現するか

消しゴム（erase）を実装するにあたっての設計判断と、その**判断基準**を記録する。
コミット単位の経緯は [commit-log.md](commit-log.md)、座標設計の採否は [README.md](README.md)、
描画方式の前提は [001 の rendering.md](../001_canvas_prototype/rendering.md) を参照。

## 前提 — immediate mode では「消す」はピクセル操作にできない

renderer は `render()` のたびに全消し → Scene の全ストローク再描画（immediate mode）。
そのため **canvas のピクセルを直接削っても、次の render で丸ごと元に戻る**。

「Scene を渡せば必ず正しい絵になる」という保証（隠れた状態を持たない）を守る以上、
消しゴムの結果も必ず Scene 側に表現されていなければならない。
つまり「消す」は canvas への塗り操作ではなく、**Scene の設計問題**である。
これがこの文書のすべての判断の出発点。

## 判断1 — 消しゴムもストロークとして積む（非破壊・追記型）

| 案 | 内容 |
|---|---|
| A. 破壊的 | erase が既存ストロークに当たり判定し、該当ストロークを削除・分割する |
| B. 追記的 | 消しゴムを erase 種別のストロークとして同じスタックに積み、描画時に `destination-out` で合成する |

**B を採用**。理由は、既存構造の不変条件をどれも壊さないこと：

- **append-only を維持** — [stroke_stack.ts](../../../src/domain/stroke/stroke_stack.ts) の
  「積まれた順・末尾が最新」にそのまま乗る
- **undo が「末尾から取り消す」のままでいられる** — A ではデータを壊すため、
  消した中身を別に退避する仕組みが別途必要になる
- **replay 可能・データ非破壊** — コマンドを順に適用すれば同じ絵になる。
  A は「消した時点で何があったか」に依存し、順序に敏感になる
- **immediate mode のループが変わらない** — 積み順に全部描く、に合成モードの
  切り替えが加わるだけ

受け入れたコスト（承知のうえのトレードオフ）：

- **データが単調増加する** — 消されたストロークもメモリに残り続ける
- **erase はそれより前に積まれたものしか消せない** — ただしこれは
  「消しゴムをかけた後にまた描いたら残る」という現実の直感と一致するため、
  制約ではなく**仕様として採用**した

## 判断2 —「消える」の粒度は合成に委ね、当たり判定を持たない

「ストローク単位で丸ごと消す」か「線の途中だけ消す（部分消し）」かは、
案 A では当たり判定とストローク分割の幾何を自前で書く必要がある。

案 B では **重なった部分が描画時に抜けるだけ**なので、部分消しが自然に出る。
当たり判定のコードを一切持たずに、消しゴムとして直感的な挙動が得られる。
「幾何の問題を合成に肩代わりさせる」のがこの設計の要点。

## 判断3 — Stroke が持つのは「ツール」ではなく「合成の役割」

[tool.ts](../../../src/shared/types/tool.ts) の `ToolType`（`pen` / `eraser` / `reset`）は
**UI で何を選んだか**であり、`reset` のようにストロークにならないものも含む。
一方 Stroke が持つべきは、描画時に**加算するのか減算するのか**という合成上の役割。

この 2 つを同じ型で縛ると altitude が合わない（将来「蛍光ペン」が増えても合成上は
加算のまま、消しゴムにプリセットが増えても減算のまま）。そこで
[stroke.ts](../../../src/domain/stroke/stroke.ts) に `KindOfTool`
（`PEN_DEFAULT` / `ERASE_DEFAULT`）を独立して定義した。
`_DEFAULT` の接尾辞は、将来プリセットが増える余地を名前に残したもの。

**判断基準**: UI の語彙と描画の語彙を同じ型で縛らない。

## 判断4 — パラメータは StrokeStyle にまとめ、Command は境界で止める

「今後パラメータが増えるなら、Command そのものを `appendPoint` に渡せばよいのでは」
という案を検討し、**採らなかった**。Command は入力・転送層の形であり、下ろすと依存が逆流する：

- **座標系が違う** — `command.point` は `ScreenPoint`、Stroke は `WorldPoint` で持つ。
  変換には camera が要るため、Command を渡すなら `stroke_stack` が camera を知る羽目になり、
  「保持はワールド・変換は境界で」という設計が保管庫に漏れる
- **転送メタデータが混ざる** — `controller_id` / `seq` / `timestamp` は
  「点をどう届けたか」であって「キャンバスに何が描かれているか」ではない

`command_dispatcher` は転送層の語彙をドメインの語彙へ翻訳する境界（anti-corruption layer）で、
`screen→world` 変換・`type→kind` の対応付け・メタデータの破棄がその仕事。ここは薄いまま保つ。

そのうえで「引数が増える」懸念自体は正当なので、受け皿を **Command ではなく
ドメイン側の値オブジェクト `StrokeStyle`**（`kind` + `radius`、ワールド単位）にした。
将来 color / opacity が増えてもこの型に足すだけで、
`appendPoint` / `createStroke` のシグネチャは安定する。

**パラメータの分類基準**:

| 種類 | 例 | 行き先 |
|---|---|---|
| スタイル | color, opacity, radius, kind | `StrokeStyle` に集約 |
| 転送・セッション | controller_id, seq, timestamp | ドメインに入れない（境界で捨てる） |
| 幾何 | point | 境界で world へ変換 |

## 判断5 — 描画状態は save/restore で 1 ストロークに閉じる

`globalCompositeOperation` は `strokeStyle` などと同じく**一度設定すると context に残り続ける**。
消しゴムで `destination-out` にしたまま戻し忘れると、**以降のすべてのストロークが消しゴムになる**。

そこで [canvas2d_renderer.ts](../../../src/infra/render-canvas2d/canvas2d_renderer.ts) の
`drawStroke` は 1 本ごとに `save()` … `restore()` で囲み、状態変更を局所化した。
あわせて、1 点ドットの分岐にあった**早期 `return` を `if/else` に組み替えた**。
early return のままだと `restore()` が飛ばされ、合成モードが後続へ漏れるため。

**判断基準**: 「戻す」を手作業の代入に頼らない。囲めば戻し漏れが構造的に起きない。

## 判断6 — 種別ごとの差分は Strategy に閉じ、幾何は共通のまま

種別によって変わるのは**合成モードと色の設定だけ**で、点列をドット／折れ線にする幾何は共通。
そこで差分のみを `StrokeRenderStrategy.prepare(context)` に閉じ込め、
`drawStroke` からは種別分岐を無くした（幾何を strategy 側に複製しない）。

テーブルを `Record<KindOfTool, StrokeRenderStrategy>` にしたのは、
**種別を追加したら strategy の実装が型で必須になる**ため（実装漏れをコンパイル時に検出できる）。

**判断基準**: 実際に変わる部分だけを抽象化する。存在しない変化を先回りして抽象化しない
（AGENTS.md「先回りしない」）。

## 入力の暫定割り当て（テスト用）

[sketch_input.ts](../../../src/features/sketch/sketch_input.ts) は通信層が入るまでの足場であり、
受信アダプタが入ったらファイルごと削除される。そのため**ツールセレクタとの本配線は行わず**、
動作確認用の割り当てだけを置いた：

- **E を押しながら左ドラッグ = 消す**。当初は右ドラッグに割り当てたが、
  トラックパッドでは右ボタンドラッグが扱いにくく、Space=移動と同じ修飾キー方式へ変更した
- 消しゴムの種別は **pointerdown 時に確定**し、途中で E を離しても 1 本は同じ種別で描き切る
  （ストロークの途中で性質が変わらないようにするため）
- `ERASE_RADIUS_SCREEN_PX = 12`（ペンは 2）は、消し跡を目視確認しやすくするためのテスト値

## 保留していること

いずれも利用箇所が出てから対応する（先回りしない）。

- **undo / redo** — 末尾 pop で成立する構造は用意できているが、コマンドは未実装
- **消えたストロークの GC・圧縮** — append-only ゆえのメモリ単調増加。性能問題が出てから
- **色・不透明度** — `StrokeStyle` に足すだけで済む形にしてある
- **ストロークの分割** — 部分消しは合成で足りているため、幾何的な分割は持たない
